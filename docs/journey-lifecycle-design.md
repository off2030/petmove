# 펫무브 여정 생애주기(Lifecycle) 설계

> 여정의 **완료 · 지난 여정 · 다중 여정 · 관련성 · 표식** 단일 출처. 작성 2026-06-08.
>
> **펫무브워크(admin) + 펫무브(portal) 양쪽 공통.** 데이터·규칙은 공유, 표시는 각 앱 톤.
>
> 관련 문서:
> - [portal-journey-design.md](portal-journey-design.md) — 여정 **step 카탈로그** 도메인(이미 구현). 이 문서는 그 위의 생애주기.
> - [follow-up-multi-destination.md](follow-up-multi-destination.md) — `by_dest`(목적지별 필드 분리) 기반.
> - [portal-plan.md](portal-plan.md) — 펫무브 앱 전체 계획.

## 0. 한눈에 (요약)

한 케이스 = 한 동물 = **N개의 여정(journey)**. 각 여정은 한 번의 출국 건.

1. **데이터는 두 층** — 동물에 붙는 사실(접종·검사: 모든 여정 공유) vs 여정에 붙는 절차(출국일·검역 등: 여정별 분리). 이미 코드에 대칭으로 존재.
2. **단위는 "목적지"가 아니라 "여정 한 건"** — 같은 목적지(예: 일본)로 2번 갈 수 있다. 여정마다 고유 일련번호.
3. **이 여정에 보일 것 = 규칙(자동) + 수동 추가 − 수동 제외** — 의료기록 사실은 동물 단위 불변, "이 여정에 관련 있나"만 여정별로 저장(양쪽 공유). 정리(추가/제외/말소)는 **펫무브워크에서만**, 보호자는 입력·수정만.
4. **완료** = 도착 자동 판정(왕복=한국 수입검역, 편도=도착) **또는** 스태프 수동 전환.
5. **지난 여정** = 완료됐거나 스태프가 전환한 여정. 양쪽에 "지난 여정" 메뉴. 읽기 전용.
6. **첫 화면** = 진행 중 여정(들)을 보여주고, 없으면 가장 최근 여정 1개.
7. **표식은 출국일 기준** — 진행 중 단일은 표식 없음 / 같은 목적지 2개는 출국월(뒤 일정 흐리게) / 지난 여정은 출국 년월일.

## 1. 배경·문제

지금까지 운영 방식(펫무브워크): **여정이 끝나면 그대로 두고, 새 목적지가 생기면 이전 목적지를 삭제**했다. 그래서 "지난 여정"이 보존되지 않았다.

바꾸려는 것:
- 끝난 여정을 **삭제하지 않고 "지난 여정"으로 보존** → 다시 열어볼 수 있게.
- 한 동물의 여러 출국(과거·현재·동시 진행)을 **한 케이스 안에서** 일관되게 표현.
- 펫무브(보호자)와 펫무브워크(스태프)가 **같은 사실·같은 판정**을 보되, 화면 톤만 각자.

> ⚠️ **과거 데이터 주의:** 기존에 삭제 방식으로 지워버린 옛 여정의 **절차 데이터(출국일·검역일 등)는 복구 불가.** 의료기록은 동물 단위라 대부분 남아 있다. "지난 여정 보기"는 **이 설계 적용 이후의 여정부터** 온전히 쌓인다.

## 2. 데이터 모델

### 2.1 두 층 — 동물 단위 vs 여정 단위 (이미 존재, 양쪽 대칭)

| 층 | 성격 | 저장 | 들어가는 것 |
|---|---|---|---|
| **동물 단위** | 한 번 일어나면 영구 사실. 모든 여정 공유 | `case.data` top-level 단일 | 마이크로칩, 광견병 접종이력(`rabies_dates`), 항체검사(`rabies_titer_records`), 종합백신/CIV, 구충 이력, 품종·생년월일, 보호자 신원 |
| **여정 단위** | 그 출국 한 건에만 의미 | `case.data.by_dest[…]` | 출국일, 항공편(가는편·오는편), 수의 임상검진, 수입허가번호, 증명서번호, 검역일, 해외주소, 구충 시각 |

이 구분은 코드에 명시돼 있다: `DESTINATION_SCOPED_FIELD_KEYS` ([packages/domain/src/destination-scoped-fields.ts](../packages/domain/src/destination-scoped-fields.ts)). 이 집합에 든 18개 키만 여정 단위, 나머지는 동물 단위.

- 펫무브워크·펫무브 **둘 다** 의료기록을 동물 단위 같은 키로 읽고 쓴다 → 한쪽에서 고쳐도 다른 쪽과 어긋나지 않음(물리적으로 같은 데이터).
- 의료기록 **수정(오타 정정)은 모든 여정에 반영되는 게 맞다** — 같은 동물의 같은 접종은 하나의 사실이므로. 여정마다 다른 값을 가질 수 없다.

### 2.2 단위는 "여정 인스턴스" (같은 목적지 2개 지원)

**문제:** 현재는 여정을 **목적지 이름**으로 구분한다(`destination` = `"일본, 베트남"` 문자열, `by_dest['일본']`). 같은 목적지가 2개면(예: 6월 일본 + 10월 일본) 키가 충돌해 둘을 구분할 수 없다.

**방향:** 여정마다 **고유 일련번호(여정 ID)**를 부여하고, `by_dest`·`trip_type` 등의 키를 **목적지 이름 → 여정 ID** 로 올린다. 목적지명은 여정의 속성이 된다.

> 이건 같은 목적지 2개만을 위한 게 아니다. **완료/지난 여정 전체의 단위가 "여정 한 건"**이기 때문이다 — 일본 6월은 "지난 여정", 일본 10월은 "진행 중"처럼 같은 목적지라도 따로 다뤄야 한다.

- 같은 목적지 3개는 없다고 봐도 됨. 2개도 극히 드묾 → 표식은 가볍게(§8).
- 이 전환은 데이터 구조 변경 범위가 있어 **구현 1단계**에서 먼저 처리(§9).

## 3. 관련성 모델 — 이 여정에 무엇을 보일까

### 3.1 보일 것 = 규칙(자동) + 수동 추가 − 수동 제외

의료기록 **사실은 동물 단위로 그대로 두고**, "이 여정에 관련 있나"(관련성)만 여정별로 저장한다(양쪽 공유). 관련성은 세 군데서 결정:

| 소스 | 예시 | 누가 |
|---|---|---|
| **규칙 (기본)** | 일본 → 종합백신 안 뜸 / 베트남 → 광견병 최신 1건만 / 중국 → 유효한 검사만(1년) | 시스템 자동 |
| **＋ 수동 추가** | 일본 여정에 종합백신 카드를 일부러 넣기 | 스태프 |
| **− 수동 제외** | 이 여정엔 불필요한 옛 기록을 빼기 | 스태프 |

- 규칙 자동 필터의 재료(목적지별 적용 step, 유효기간 — 항체 2년·백신 valid_until 등)는 이미 도메인에 있다([journey-steps/applicability.ts](../packages/domain/src/journey-steps/applicability.ts), [procedure-checks/](../packages/domain/src/procedure-checks/)).
- 목적: 여정 타임라인에 **그 여정에 관련된 것만** → 깔끔. 동물 이력에는 다 쌓이되(정상), 여정 화면엔 비대해지지 않음.

**예시 — 일본 + 종합백신:**
1. 일본 여정 → 규칙상 종합백신 단계 안 뜸.
2. 스태프가 펫무브워크에서 일본 여정에 "종합백신 추가" → 그 여정의 관련성에 저장(공유 DB).
3. 보호자가 펫무브에서 같은 일본 여정을 열면 → **종합백신 카드가 새로 떠 있음.**
4. 종합백신 기록 자체는 동물 단위라 다른 여정에서 보이던 그 기록과 같은 하나(복사 아님).

### 3.2 삭제 2종 (결과는 양쪽 공유)

| 동작 | 의미 | 동물 이력 | 다른 여정 |
|---|---|---|---|
| **여정에서 빼기** | 이 여정 화면에서만 숨김 (관련성 제거) | 보존 | 영향 없음 |
| **사실 말소** | 기록 자체 삭제 (정정) | 삭제 | 모두 반영 |

대부분은 규칙 자동 필터가 처리하므로 수동으로 뺄 일은 드물다.

### 3.3 권한

| 동작 | 펫무브(보호자) | 펫무브워크(스태프) |
|---|---|---|
| 기록 입력·수정(날짜·값, 오타 정정) | ✅ | ✅ |
| 여정에 추가 / 여정에서 빼기 | ❌ | ✅ |
| 사실 말소(삭제) | ❌ | ✅ |
| 여정을 지난 여정으로 전환 | ❌ | ✅ |

→ 보호자는 **입력·수정만**, 모든 정리(추가·제외·말소·전환)는 스태프. 보호자 실수로 지난 여정이 망가질 일이 없다. (모든 동작의 **결과**는 양쪽에 반영됨.)

## 4. 완료

여정이 "완료"가 되는 경로 두 가지 (둘 중 하나):

| 경로 | 조건 | 누가 |
|---|---|---|
| **자동** | 도착 판정(`has-arrived`) — 왕복=한국 수입검역 확인, 편도=도착(일본 편도는 일본 수입검역 확인으로 명확) | 시스템 |
| **수동** | 펫무브워크에서 스태프가 "지난 여정으로 전환" | 스태프 |

- 자동 판정(`has-arrived`)은 [done-resolver.ts](../packages/domain/src/journey-steps/done-resolver.ts)에 이미 있음. portal은 완료 시 도착 배너(스탬프 + 소감 남기기)를 띄움.
- **수동 전환의 실제 용도:** 정상 완료여도 **고객이 임상검사·검역 "완료"를 안 누르고** 다녀오는 경우가 흔하다 → 자동 완료가 안 뜸 → 고객에게 완료를 강요하긴 이상하니 **스태프가 강제 전환**. (드물게 취소·중단 정리에도 사용.)

## 5. 지난 여정

### 5.1 전환 조건

§4의 완료(자동) **또는** 스태프 수동 전환 → 그 여정은 "지난 여정". 양쪽 앱에 **"지난 여정" 메뉴/섹션**. 지난 여정은 **읽기 전용**(끝난 일정 수정 불가).

- 보호자(펫무브)는 **자동(도착)**으로만 지난 여정이 됨.
- 스태프(펫무브워크)는 자동 + **수동 전환** 둘 다.
- "지난 여정"의 그때 증빙(발급 서류 PDF)은 불변 파일로 보존. 의료기록은 §3대로 그 여정에 관련됐던 것이 보임.

### 5.2 운영 방식 변화

- **이전:** 새 목적지 = 이전 목적지 삭제.
- **이후:** 새 목적지는 **병렬로 추가**, 이전 여정은 완료/수동 전환으로 **지난 여정으로 보존**. 새 목적지를 등록한다고 진행 중 여정이 자동으로 내려가지 **않음**.

## 6. 첫 화면 규칙

> - **진행 중 여정이 있으면** → 그것(들)을 첫 화면에 (여러 개면 병렬로 다)
> - **진행 중 여정이 없으면** → 가장 최근(완료일 기준) 여정 1개를 첫 화면에
> - **나머지** → "지난 여정" 메뉴로

케이스 대입:

| 케이스 상황 | 첫 화면 | 지난 여정 메뉴 |
|---|---|---|
| 일본만 진행 중 | 일본 | 비어 있음 |
| 일본·베트남 둘 다 진행 중 | 일본 + 베트남 (병렬) | 비어 있음 |
| 일본 완료, 다른 여정 없음 | 일본 (완료 카드 그대로) | 비어 있음 |
| 일본 완료 + 베트남 진행 중 | 베트남 | 일본 |
| 일본·베트남 둘 다 완료 | 베트남 (가장 최근) | 일본 |

## 7. 양쪽 앱 일관성

**원칙: 동작(사실·판정)은 공유로 보장, 표시(화면)는 각 앱 톤.**

- **공유에 둘 것** — 관련성 판정(규칙), 추가/제외 데이터, 완료 판정, 지난 여정 상태. `case.data`(데이터) + `packages/domain`(규칙)에 두면 양쪽이 같은 결론. (검증 규칙을 양쪽이 공유하는 기존 패턴과 동일.)
- **각 앱 톤** — 펫무브워크 = 스태프용 입력 폼(데스크톱 정보 밀도), 펫무브 = 보호자용 타임라인·카드(모바일 Calm).
- **표시 정책 차이 허용** — 같은 판정이라도: 펫무브는 관련 없는 옛 기록을 **숨김**, 펫무브워크는 전체를 보여주되 "이 여정엔 유효/만료" **배지**로 — 같은 사실, 두 표현.

**현재 비대칭 (펫무브워크 변경량이 더 큼):**
- 펫무브: journey-steps 카탈로그·타임라인·완료(`has-arrived`) 배너 **있음** → 확장에 가까움.
- 펫무브워크: journey 카탈로그 **안 씀**, 의료기록을 **항상 전체**로 표시, 케이스 `status` 컬럼은 과거에 **삭제**된 이력([20260430000001_drop_cases_status.sql](../supabase/migrations/20260430000001_drop_cases_status.sql)). → "관련성 필터 + 지난 여정 + 수동 전환/추가·제외 UI"가 새로 들어감.

## 8. 표식 규칙

**모든 날짜 표식은 "출국일" 기준으로 통일.** (보호자 기억과 일치, 편도·왕복 일관, 진행 중 구분과 통일.)

| 상황 | 표식 |
|---|---|
| 진행 중 · 목적지 다름 | **일본** / **베트남** (표식 없음) |
| 진행 중 · 같은 목적지 2개 | **일본 · 6월** / *일본 · 10월* (뒤 일정 흐리게) |
| 진행 중 · 출국일 미정 | **일본 · 준비 중** (출국일 정해지면 월로 전환) |
| 지난 여정 | *일본 · 2025.06.23* (출국 년월일, 흐리게 + ✓) |
| 지난 여정 상세(펼침) | 2025.06.23 출국 ~ 2025.11.15 귀국 (왕복) |

세부 규칙:
- **"한국 ⇄ 일본" 왕복 표시는 유지** — 불필요한 정보지만 여행 이미지를 강화(사용자 결정). 헤더 라우트는 [case-header.tsx](../apps/portal/components/cases/case-header.tsx)가 담당, 목적지 2개+ 면 탭→바텀시트 전환.
- **뒤(나중 출국) 여정은 흐리게** — `ink-2`(#6B6457) → `ink-3`(#9A9286). "흐린 게 나중"이라는 약한 단서까지 생김. 색약에도 명도 차로 안전.
- **헤더는 짧게, 바텀시트는 출국월 곁들임** — 평소 헤더는 색만(깔끔), 탭해서 여는 바텀시트(목록)엔 "6월 출국 / 10월 출국"을 함께 → 정확히 어느 게 먼저인지 확인 가능.
- **진행 중**(헤더 메인)은 월만(올해 가정, 해가 다르면 연도), **지난 여정**(목록·상세)은 년월일 — 위치가 달라 길이 부담이 다름.
- 날짜 표기 형식(`2025.06.23` 점 vs `2025년 6월 23일` 한글)은 시안에서 최종 확정.

## 9. 구현 영향 + 단계

> 디자인은 [docs/portal-preview/](portal-preview/) 시안을 먼저 고치고 코드에 반영([apps/portal/CLAUDE.md](../apps/portal/CLAUDE.md) §5).

대략의 순서(각 단계 독립 커밋·배포 가능하게):

1. **여정 인스턴스 모델** (데이터 근간) — `destination` 문자열·`by_dest`·`trip_type` 키를 목적지명 → 여정 ID 로. 백필 마이그레이션. 같은 목적지 2개 지원의 토대. → 상세 설계: [journey-id-migration.md](journey-id-migration.md) (방식 A·마이그레이션·전환 순서·위험).
2. **관련성 저장 + 규칙 필터** (공유 도메인) — "이 여정에 보일 것 = 규칙 + 추가 − 제외" 판정 함수를 `packages/domain`에. 추가/제외 데이터를 `case.data`에.
3. **완료·지난 여정 상태 + 첫 화면 규칙** (공유) — 완료 판정(기존) + 수동 전환 플래그 + "진행 중 우선/없으면 최근" 선택 로직.
4. **펫무브(portal) UI** — 타임라인에 관련성 필터 반영, "지난 여정" 메뉴, 표식(출국일·흐림·완료), 바텀시트 출국월.
5. **펫무브워크(admin) UI** — 의료기록 섹션을 "여정 관련만 + 유효/만료 배지", 수동 추가/제외·전환 버튼, "지난 여정" 메뉴.
