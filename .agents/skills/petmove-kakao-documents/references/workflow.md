# 수신 자료 다운로드·보관·구조화 입력

## 원본 다운로드와 내용 대조

1. 현재 상담 페이지의 실제 DOM/화면에서 파일명·사진·저장 링크를 확인한다. 과거 탭 ID·요소 인덱스·메시지 ID·다운로드 URL을 재사용하지 않는다.
2. 현재 브라우저의 지원 API로 다운로드한다. `waitForEvent('download')`를 **저장하기 클릭 전에** 시작하고 다운로드 결과의 실제 경로를 받는다. 아래는 현재 도구에서 검증한 패턴이며 `tab`과 `saveLink`는 현재 상담 페이지와 실제 확인한 저장 링크다. API가 바뀌면 제공된 문서를 우선한다.

   ```js
   const [download] = await Promise.all([
     tab.playwright.waitForEvent('download', { timeoutMs: 15000 }),
     saveLink.click(),
   ]);
   const localPath = await download.path();
   ```

3. 실제 파일 생성·크기·열림을 확인하고 이미지/PDF 내용을 읽는다. 보호자명·동물명·칩번호·문서 날짜 등 문서에 노출된 식별값을 현재 케이스와 대조한다. 수첩의 일부 페이지처럼 식별값이 없는 사진은 같은 고객의 수신 묶음·앞뒤 대화와 접종일·제품·로트 등 공통 근거로 연결한다. 근거가 부족하면 임의로 다른 케이스에 저장하지 않는다.
4. 검사결과지와 검사기관의 발송 안내 캡처는 별개 자료로 구분한다. 고객 캡처에 적힌 발송 내용을 독립적으로 확인한 기관 접수·승인으로 표현하지 않는다.
5. 원본은 보존하고 필요한 경우 종류를 알 수 있는 파일명으로 복사한다. 회전·변환본이 필요하면 원본과 구분한다. 로컬 작업 폴더는 생성 **전에** `git check-ignore` 등으로 Git 제외 여부를 확인한다. 현재 `/work/naver-inquiries/`는 제외된 업무 작업 위치이며 임의의 새 `work/` 하위 폴더도 제외됐다고 가정하지 않는다. 고객 파일·서명된 URL·대화 원문은 Git이나 스킬에 넣지 않는다.

## 다운로드 오류의 정상 복구

첫 오류만으로 바로 사용자에게 다운로드를 맡기지 않는다. 실패 원인을 확인하고 다음 중 해당하는 정상 복구를 수행한다. 같은 조작을 이유 없이 반복하지 않는다.

- 클릭 시간 초과·빈 결과는 성공/실패의 확정 근거가 아니다. 실제 다운로드 결과·로컬 파일·현재 탭을 확인해 중복 다운로드를 피한다.
- AX 결과가 이전 상담 내용을 보여도 실제 탭은 이미지 CDN/오류 페이지로 이동했을 수 있다. 현재 탭 URL과 새 DOM snapshot으로 실제 페이지를 확인한다. 이전 인덱스·오래된 AX 결과로 다음 파일을 누르지 않는다.
- 출처나 탭 연결이 오래됐으면 같은 연결된 Chrome에서 **관찰한 정상 상담 URL**로 돌아가거나 새 상담 탭을 열고, 로딩 후 새 DOM으로 대상과 저장 링크를 다시 확인한다. `about:blank`에서 바로 파일 URL로 이동하지 말고 실제 상담 출처가 준비됐는지 확인한다. 새 탭이 필요해도 브라우저 연결 자체를 불필요하게 재선택하지 않는다.
- 정상 상담 페이지가 복구된 후 지원되는 다운로드 대기와 실제 저장 링크 클릭을 함께 실행한다. 파일별로 다운로드 완료와 현재 페이지를 확인한 뒤 다음 파일을 진행한다. 이 방식으로 상담 연결 복구 후 다수 원본을 자동 저장한 실적이 있다.
- 다운로드 권한/출처 보안 확인 실패는 임의로 우회하지 않는다. 정상 페이지 연결 등 원인이 해소된 경우에만 재시도한다. 보안 경고 무시, 보호기능 해제, 쿠키 추출·별도 HTTP 요청으로 차단을 피하는 방법은 사용하지 않는다. 지원되는 복구로 해결되지 않거나 로그인·MFA·CAPTCHA가 필요하면 구체적인 오류·시도한 복구·현재 저장된 파일·남은 작업과 필요한 최소 사용자 조치를 보고한다.

## 펫무브워크 저장과 검증

- 업로드 직전에 현재 케이스의 기존 첨부를 다시 확인한다. 재개 시 이미 저장된 파일명·크기·내용을 대조해 중복 업로드하지 않는다. 이전에 일부 성공했다면 남은 파일만 처리한다.
- 일반 수신 자료는 해당 케이스의 **보관함**에 원본을 저장한다. `추가정보`의 자동 추출이나 `수입 허가증` 등 완료 신호를 만드는 첨부란과 혼동하지 않는다. 이 요청만으로 구조화 필드를 자동 추출·저장하지 않는다.
- 현재 화면의 `보관함` 파일 선택 기능과 지원되는 `filechooser`/`setFiles`를 사용한다. 복수 선택 가능 여부를 확인하고 파일 목록과 실제 업로드 완료를 확인한다. 직접 저장 경로를 써야 한다면 현재 앱의 첨부 모델과 기존 데이터 보존·동시 변경 방지를 먼저 확인한다.
- 업로드 결과가 불명확하면 반복 업로드 전에 현재 저장값을 재조회한다. 같은 조직·케이스의 첨부 이름·수량·크기를 직접 조회하고, 저장 파일을 다시 읽어 원본 바이트/해시와 대조한다. 기존 메모·첨부와 검사/신고·여행 데이터가 보존됐는지도 확인한다.
- 최종 보고는 보호자·동물, 저장한 자료 종류와 수량, 검증 결과를 간결히 전한다. 보관함 목록이 보이는 결과 화면을 보존한다. 누락·대상 불일치·저장 실패가 있으면 완료라고 하지 말고 실제 저장분과 남은 작업을 구분한다.

## 서류 근거로 칩·접종·항체검사 정보 입력

입력 요청 범위를 먼저 확인하고, 해당 서류와 현재 저장값을 대조한다. 아래 필드는 현재 앱의 저장 구조이며 실행 때 소비 코드도 확인한다. 증빙에서 읽을 수 없는 값은 추정하지 않고 기존 값을 보존한다. 실제 증빙끼리 충돌하면 해당 항목의 양쪽 근거를 보고하며 임의로 하나를 정답으로 선택하지 않는다. 제품명·제조사명·브랜드명은 구분하고 약칭의 동일성이 확인되는 경우에만 정규화한다.

| 항목 | 읽을 근거와 저장 기준 |
| --- | --- |
| 칩 삽입일 | 증명서의 이식일/식별일 라벨과 현재 칩번호를 대조해 `data.microchip_implant_date`에 저장. 생년월일·증명서 발급일을 대신 쓰지 않는다. |
| 광견병 접종 | `data.rabies_dates`의 해당 접종일 기록에 `date`, `product`, `manufacturer`, `lot`, `valid_until`, `expiry`, `other_hospital`을 기존 UI 규칙대로 반영한다. `apps/admin/components/cases/repeatable-date-field.tsx`와 `apps/admin/lib/actions/extract-vaccine.ts`를 확인한다. |
| 면역 유효기간 | 증명서의 1Y/2Y/3Y는 `valid_until`의 `1년`/`2년`/`3년`이다. 제품 유통기한 `expiry`와 구분하며 접종일로부터 계산한 날짜로 바꾸지 않는다. |
| 제품 유통기한 | 명시된 EXP/유효기한만 `expiry`에 저장한다. 연월만 명시된 EXP는 기존 앱의 추출 규칙에 따라 그달 말일로 정규화하고 보고에서 설명한다. 접종일·면역기간으로 EXP를 만들지 않는다. |
| 타 병원 접종 | 실제 접종 병원이 본원인지 확인한다. 타 병원 증명서·수첩 기록이면 `other_hospital: true`를 유지/반영하며 본원 제품 기본값으로 덮지 않는다. 타 병원 접종을 본원 증명서로 재작성하지 않는다. |
| 항체검사 | 결과지의 **채혈일**·결과 수치·검사기관을 `data.rabies_titer_records`의 해당 회차 `date`, `value`, `lab`에 저장한다. `apps/admin/components/cases/rabies-titer-field.tsx`의 규칙을 따른다. 수치는 단위 없이 저장하고 비교부호가 있으면 보존한다. |
| 검사 날짜 구분 | 검사결과지 발급일·검사 신청일을 채혈일로 입력하지 않는다. `received_date`는 실제 샘플 수령일이 명시되고 해당 여행에서 쓰일 때만 반영하며 발급일로 대체하지 않는다. |

- 대상 접종일·검사일·기관과 기존 기록을 대조해 같은 회차를 갱신한다. 배열 첫 항목으로 단정하지 않는다. 없는 회차만 추가하고, 여러 후보가 있으면 자료를 더 대조한다. 기존 다른 회차·첨부·메모·여행·상태를 보존한다. 정보 입력만으로 검사/신고 상태를 별도로 완료 처리하지 않는다.
- 기관 선택지는 해당 조직의 `organization_settings.inspection_config`와 `effectiveTiterLabs`/`allLabOptions`가 기준이다. 중앙백신연구소(Choong Ang Vaccine Laboratory)의 사용자 지정 표시명은 **CAV Lab**이다. 현재 로잔 조직에는 저장 식별값 `Choong Ang Vaccine Laboratory`, 표시명 `CAV Lab`의 사용자 정의 항체검사 선택지가 등록되어 있으므로 실행 시 최신 설정을 읽어 해당 선택지를 사용한다. 정식 영문명이 필요한 PDF의 원시 식별값을 표시 약칭으로 무조건 바꾸지 않는다.
- 기관이 선택지에 없으면 다른 기관 코드로 대체하지 않는다. 앱이 지원하는 직접입력으로 실제 기관명을 보존할 수 있는지 확인한다. 조직 선택지 추가는 별도 사용자 지시가 있을 때 기존 설정을 보존해 수행하고 선택 목록까지 검증한다. 한 기관을 추가한다는 이유로 기본 기관·국가별 자동 선택 규칙을 변경하지 않는다.
- UI 또는 승인된 직접 저장 경로를 사용한다. 직접 갱신 시 조직·케이스 ID를 명시하고 최신 `updated_at` 등으로 동시 변경을 확인하며 허용된 필드만 병합한다. 읽기 전용 조회 스크립트에 쓰기 기능을 추가하지 않는다. 동시 변경이면 다시 읽고 대조하며 오래된 JSON으로 덮어쓰지 않는다.
- 저장 후 DB를 직접 재조회하여 각 값·회차와 나머지 정보 보존을 확인한다. JSON 객체 키 순서는 의미가 없으므로 문자열 순서 비교 실패만으로 재저장하지 말고 구조적 동등성으로 검증한다. 결과가 불명확하면 현재 저장값부터 확인해 중복 회차를 만들지 않는다.
- 보고에는 칩 삽입일, 접종일·제품·제조사·제조번호·면역기간·제품 EXP, 항체 채혈일·기관·수치를 간결히 적는다. 읽지 못했거나 충돌해 미반영한 항목, 월 단위 EXP 정규화도 구분한다. 실제 고객의 값·칩번호·첨부파일 경로는 이 스킬에 고정하지 않는다.
