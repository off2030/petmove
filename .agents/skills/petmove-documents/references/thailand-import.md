# 태국 반려동물 수입허가 이메일 신청

서류 및 기타 담당의 태국 신청 절차다. 권한·공식 상태·잠금·공유 이력은 [공통 실무 기준](../../../../docs/work-management/operations.md)을 따른다. 준비 요청과 기관 발송 지시를 구분한다. 사용자가 검토한 신청의 발송을 지시하면 동일 작업의 승인을 반복해서 묻지 않고 발송과 Work 반영까지 마친다. 이 절차 저장만으로 새 대상 일괄 발송·고객 안내·다른 국가 신청 권한을 만들지 않는다.

## 계정·여행·기존 신청 확정

- 현재 Work DB와 UI/PDF의 실제 선택 함수로 조직·케이스·태국 여행 차수·영문명·국적·칩·접종·체류지·항공편을 확정한다. 분리 영문명과 과거 합본 이름이 다르면 실제 소비 규칙을 먼저 확인한다. 여권 국적을 한국 주소에서 추정하지 않는다.
- Gmail은 사용자가 지정한 계정을 사용한다. 태국 신청의 기본 업무 계정은 **펫무브 Gmail**이며, 화면 표시명만 보고 로잔 또는 개인 계정으로 바꾸지 않는다. 접속 계정 식별자는 연결 도구에서 직접 확인한다.
- 같은 동물·칩·여행의 기존 SENT·기관 회신·공유 위임을 먼저 확인한다. 초안/발신 결과가 불명확하면 기존 메시지부터 재조회하고 중복 발송하지 않는다.
- 실제 도착 공항 담당 검역소와 최신 공식 제출 시기·접종 요건을 확인한다. 치앙마이(CNX)는 `qscm_cmi@dld.go.th`가 확인된 신청처이나, 실행 때 공식 안내와 최근 기관 회신을 다시 대조한다. 다른 공항 주소를 함께 참조에 넣지 않는다.
- 공식 안내 출발점: [태국 공관 안내](https://cgchicago.thaiembassy.org/en/page/bringing-pets-to-thailand-2/). 기존 발신·승인 메일은 작성 예시이며 최신 요건의 대체 근거가 아니다. 신청 가능 기간과 영업일, 백신 경과일을 실제 도착일로 계산한다.

## 서류 준비

1. R1/1은 Work의 실제 `Form_R11` 생성 경로를 사용한다. 여권 기준 신청자 이름·국적·발급기관, 동물 정보, 칩, 한국/태국 주소, 도착편·도착 현지 날짜/시각을 대조한다. 태국 불기 연도와 빈 직업란을 임의 값으로 채우지 않는다.
2. 접종·칩 증명서는 실제 `Form25` 옵션과 조직의 등록 수의사·백신 카탈로그를 사용한다. 발급 지시가 있으면 확인된 접종 기록에 대해 발급일과 등록 서명을 적용한다. 접종 증명서 발급을 새 임상 진찰·건강 확약이나 정부 검역 완료로 바꾸지 않는다. 타 병원 기록을 본원 기본 제품으로 대체하지 않는다.
3. 사용자가 지정한 태국 신청의 기본 준비 방식은 **R1 서명란에 현재 보호자의 확인된 한글 이름을 자연스러운 손글씨체로 기입**하는 것이다. 이 준비 방식을 매번 다시 묻지 않는다. 실제 서명 이미지를 받은 경우 그대로 사용하며, 기관이 실제 서명을 별도로 요구하면 그 요구를 따른다. 글꼴 이름 기입을 보호자가 직접 서명한 사실로 기록하거나 실제 서명을 복제했다고 표현하지 않는다.
4. Work의 원본 백신북 사진도 모두 확인한다. 신원 페이지, 종합백신, 광견병 페이지의 동물·칩·접종일·제품·로트·병원 표시를 대조한다. 다음 접종 예정일이나 제품 유효기간을 실제 접종일/면역 유효기간으로 오인하지 않는다. EXIF 방향을 바로잡고 원본을 자르지 않는다.
5. 여권, 도착편이 표시된 전체 항공 일정표, 동물 사진을 대조한다. 항공권의 귀국편이 Work에 없으면 별도 후속으로 남기며 신청 준비 중 임의로 여행 일정을 바꾸지 않는다. 출발 전 정부 건강·수출검역 증명서는 별도 최종 단계다.

## 통합 PDF와 이메일

기본 배치는 **R1/1 → 접종·칩 증명서 → 백신북(신원·종합·광견병) → 여권 → 항공 일정표 전체 페이지 → 동물 사진**이다. 자료 수에 따라 페이지 수는 달라지며 특정 케이스의 9페이지를 고정 규칙으로 삼지 않는다. 추가 기관 요구가 있으면 관련 문서 뒤에 배치한다.

- 문서별 제목, 연속 페이지 번호, 책갈피를 넣어 한 PDF로 정리한다. 사진은 가독성을 유지하고 본문·서명·도장을 가리지 않는다. 개별 원본과 수정 가능한 서식을 보존한다. 통합본에서 폼을 정적 페이지로 조립할 때 원래 필드의 표시값·체크·서명이 빠지지 않았는지 확인한다.
- 모든 페이지를 렌더링해 방향·가독성·누락·잘림·서명·숫자를 검토한다. CJK 글꼴은 실제 저장 PDF에서 확인한다. 서브셋 글꼴로 글자가 빠지면 전체 글꼴 임베딩 등으로 해결한 뒤 다시 검토한다.
- 초안은 내부 검토 표시와 미비 사항을 명시할 수 있다. 발송 지시를 받으면 제목/본문의 내부 메모, `REVIEW`·`UNSENT` 및 PDF의 검토본 표시만 제거한다. 임상 사실·날짜·기입 내용·정부 확인을 바꾸어 최종본처럼 꾸미지 않는다.
- 영어 메일은 신청 목적, 신청자·동물·칩, 도착편·현지 도착일/시각, 태국 주소, 첨부 목차와 업무 서명을 간결히 적는다. 실제 수신처·발신 계정·참조를 확인하고 통합 PDF **하나**를 첨부한다. 기관이 개별 파일을 요구한 경우는 그 요구를 따른다.
- 기존 Gmail 초안의 본문·첨부를 수정한다. 연결 도구의 `update_draft`는 payload를 제공하면 MIME 전체를 교체하므로 첨부가 유실되지 않게 한다. 첨부 교체 기능이 부족하면 연결된 Chrome의 브라우저 전용 도구로 수정하고 Gmail 도구로 저장된 초안을 재조회한다. Windows 전체 제어로 대체하지 않는다.

## 발송·Work 반영·회신

발송 직전 실제 저장 초안의 To/From/Subject/본문과 첨부명·크기를 다시 읽는다. 발송 후 **SENT 라벨·수신처·발신 시각·실제 첨부**를 재조회한다. 발송 실패/불명확은 진행으로 바꾸지 않으며 같은 메일을 먼저 조회한다.

공통 권한에 따라 실제 발송을 확인한 실행에서 해당 태국 여행 수입을 **진행(in_progress)** 으로 저장·직접 재조회한다. 현재 `setReportSlotStatus`와 `resolveReportBinding`·`planReportSlotWrite`·`writeByDestValue`의 소비/저장 규칙을 사용하며 기존 다른 여행·필드·첨부를 보존한다. Gmail 메시지 ID를 허가번호에 넣지 않고, 신청 자료를 `import-permit` 발급 원본 첨부로 보관해 완료가 조기 파생되게 하지 않는다.

수신 확인·검토·보완·허가 발급은 별개다. 원래 발신 스레드와 첨부 원본을 후속의 기준으로 남기고, 기관 승인 원본의 동물·칩·여행·유효기간 대조와 보관을 마친 후 해당 여행만 완료로 반영한다. 메시지 ID·파일 지문·실행 근거·남은 행동은 비공개 공유 이력에, 공식 수입 상태는 Work에만 둔다. 현재 사용자 권한에 없는 보완 발송이나 임상 정정은 그 범위를 먼저 확정한다.

고객명·여권·칩·메일 원문·실제 서명 이미지·비밀번호는 이 문서나 Git에 저장하지 않는다.
