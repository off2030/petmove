# InterCommerce 기관 조작

아래 주소와 라벨은 확인된 탐색 단서다. 현재 화면·URL을 읽고 지원되는 브라우저 도구로 조작한다. 변경된 DOM에 과거 선택자나 주소를 맹목적으로 적용하지 않는다.

## 계정과 신청 찾기

- 신규 등록: [BAI registration](https://www.intercommerce.com.ph/registrationbai.asp). 기존 계정·등록 여부부터 확인한다. **사용자 상시 지시에 따라 TIN은 해당 보호자의 현재 여권번호로 입력**한다. 별도 TIN을 매번 묻지 않으며 여권번호 자체가 없거나 불일치할 때만 확인한다. Company N/A 등 다른 값은 현재 안내와 실제 신청자 조건을 대조한다.
- [로그인](https://www.intercommerce.com.ph/login.asp?home=HOME) → 회원 메뉴 → WebCWS → `Create/Open BAI OneTimeImporter` → 실제 Importer 선택 → 기존 목록 확인 → 신규 신청 또는 기존 신청 열기.
- 로그인 아이디는 **보호자 이메일**을 사용한다(사용자 확인 기준). Work의 현재 이메일과 기존 등록 계정을 대조하며, 이메일 변경 등 모순이 없으면 이미 확인된 아이디를 다시 묻지 않는다. **비밀번호는 이미 사용자가 지정한 공통값을 아래 로컬 저장소에서 불러오고 반복해서 묻지 않는다.** 비밀번호 평문은 이 스킬·Git·공유 이력·예약 프롬프트에 넣지 않는다.
- 주요 화면: `cws_ic_step0DA1tym.asp`, `cws_ic_step1DA1tym.asp`, `cws_ic_step2DA1tym.asp`, 본문 `cws_ic_impdecDA1tym.asp`.
- 기존 내역을 조회할 때는 `Open an Existing Application` **라디오 자체를 선택하고 checked 상태를 확인한 뒤** Next를 누른다. 같은 문구의 링크를 누르는 것만으로는 선택되지 않을 수 있다. 다음 목록의 제목도 `Open an Existing Application`인지 확인한다. `Create From an Existing Application`이면 링크 선택으로 복제 초안이 생성되므로 조회 목적으로 신청번호를 누르지 말고 이전 단계에서 선택을 바로잡는다. 본문 진입 후에도 원래 신청번호·상태를 대조한다.
- 계정·Importer 이름·여권이 현재 대상과 일치하는지 **본문에서도** 재확인한다. 다른 사람 정보가 보이면 멈추고 올바른 계정으로 다시 들어가 기존 목록부터 확인한다. 비활성 사람 정보를 강제로 수정하지 않는다.

### 지정 비밀번호 불러오기

사용자가 지정하고 저장을 요청한 InterCommerce 공통 비밀번호는 Windows 현재 사용자 DPAPI로 암호화하여 `%LOCALAPPDATA%\Petmove\Credentials\intercommerce-default.dpapi`에 보관한다. 암호문도 Git·Drive로 복사하지 않는다. 다른 PC에는 자동으로 이전되지 않는다.

- 이 스킬의 `scripts/intercommerce-credential.ps1`을 PowerShell에서 dot-source하고 `Read-PetmoveInterCommercePassword`로 `SecureString`을 받는다. **허용된 기존 계정 로그인 또는 사용자가 요청한 신규 가입의 최초 비밀번호 입력**에는 지정된 값을 로컬 메모리에서만 복원해 브라우저 입력에 전달하고 즉시 참조를 해제한다. 명령줄 인자·도구가 반환하는 표준 출력·도구 결과·로그·클립보드에 평문을 노출하지 않는다.
- 읽기 실패 시 비밀번호를 추측하거나 다시 저장하지 않는다. 저장소 미설정·Windows 사용자/PC 변경·기관 거절 등 실제 사유를 설명한다. 비밀번호가 저장되어 있어도 계정 미가입과 오입력을 구분하고, 오류 뒤 같은 값으로 반복 로그인하지 않는다.
- **기존 계정 비밀번호 변경·재설정과 신규 가입의 최초 비밀번호 설정을 구분한다.** 사용자가 신규 가입과 지정 비밀번호 사용을 요청했다면 최초 비밀번호·확인 칸을 입력하며, 기존 자격 증명 변경의 사용자 인계 규칙을 이 단계에 확대 적용하지 않는다. 기존 비밀번호 변경·재설정, 약관·CAPTCHA·최종 제출·비용은 각각 해당 시점 도구 정책과 실제 권한을 확인한다. 지정된 값을 다시 알려달라고 요구하지 않는다. 비밀번호 저장 자체로 별도 가입·제출 권한이 생기지는 않는다.

## 본문과 동물

1. 목적 Pet, 출발국, 실제 입국 공항/항구·운송 수단·검역 장소·필리핀 주소 등 현재 필수값을 원본 여행과 대조해 입력한다. 이전 건의 AIR/Metro Manila/공항을 기본값으로 복제하지 않는다.
2. 품목 검색 팝업 `Lookup-ImportablesDA1tym.asp`에서 실제 Dogs/Cats를 조회·선택한다. 상품번호·HS/AHTN은 포털 선택 결과를 사용하고 개의 코드를 고양이에 복제하지 않는다.
3. 동물별 수량·중량·품종·신청일 기준 월령·성별·칩을 입력한다. `cws_ic_item-detailDA1tymE.asp`의 저장 후 본문 목록·수량·대상을 재조회한다. 여러 마리는 개별 칩·첨부 연결을 검증한다.
4. Save와 상태 Created/Incomplete는 초안 저장이다. 실제 접수는 별도다.

## 파일 업로드

본문의 파일 업로드를 열면 `file_uploader/index.php?appno=...`가 표시된다. 현재 슬롯과 요구 형식을 읽는다. 확인된 슬롯은 `proof_of_microchip`, `vaccination_record`, `photographs`, `pet_passport`다. 같은 서명 증명서가 칩·백신·구충을 모두 증명하면 적합한 슬롯에 재사용할 수 있으나 실제 내용을 먼저 대조한다. Pet passport 대체 서류 허용 여부도 현재 화면으로 확인한다. 2027 서식 변경 시 슬롯명보다 현행 서류 요건을 우선한다.

지원되는 file chooser/setFiles로 업로드하고 선택된 파일명·크기·화면을 확인한다. 표시된 크기 제한을 파일별/전체로 구분해 적용한다. 용량을 줄이면 원본은 보존하고 파생본의 전 페이지 가독성을 확인한다. 파일 선택 실패를 근거 없이 Chrome 파일 URL 권한 문제로 단정하지 않는다.

첨부 팝업의 DOM은 읽히지만 클릭이 `Input.dispatchMouseEvent` 시간 초과로 실패하면 같은 클릭을 반복하지 않는다. 부모 신청번호를 확인·보존한 뒤, **실제로 열린 업로더의 같은 URL**을 일반 새 활성 Chrome 탭으로 열어 file chooser를 다시 시도한다. 새 신청이나 복제 초안을 만들지 않으며, 현재 파일 선택·저장 결과부터 확인해 이중 업로드를 피한다. 이 복구는 관찰한 기관 화면의 정상 탐색이며 브라우저 접근 차단을 우회하는 방법으로 사용하지 않는다.

**업로더 Submit은 첨부 저장이다.** `Success! Attachments has been uploaded.`는 허가 신청 완료가 아니다. 확인 알림을 닫고 부모 신청의 첨부 저장 여부를 확인한다. DOM에서 FileList를 읽지 못해도 파일이 선택됐을 수 있으므로 파일명/화면·실제 업로드 결과로 판단한다.

브라우저 도구가 알림 없음이라고 해도 네이티브 JavaScript 알림이 페이지를 막을 수 있다. 타임아웃 뒤 현재 스크린샷·지원되는 dialog API로 확인한다. 보이지 않거나 도구로 닫히지 않으면 사용자가 알림을 닫도록 요청하고 현재 신청번호·부모 탭 재개 위치를 보존한다. 같은 파일·신청을 반복 전송하거나 이미 저장된 신청을 새로 만들지 않는다.

## 최종 접수와 복구

Send → `cws_check-msgDA1tym.asp`의 오류·신청번호·현재 CERTIFICATION 전체를 검토한다. 요건 증거·비용 권한을 다시 확인한다. 현재 도구가 해당 시점 사용자 확인을 요구하면 실제 문구와 범위를 제시하고 대기한다. 유효한 승인 범위에서 `I Agree → Continue`를 진행한다.

`cws_res-msgDA1tym.asp`의 **해당 신청번호 UNDER REVIEW**, 현재 목록의 같은 상태를 확인하고 접수 증거를 비공개로 보관한다. 화면만 닫혔거나 시간 초과면 목록을 다시 열어 이미 접수됐는지 먼저 확인한다. Success/No errors/Created는 최종 접수 증거로 대체하지 않는다. 잔액 차감이 있으면 실제 금액과 결과를 기록·보고한다. 최종 화면은 사용자가 확인할 수 있게 유지한다. 브라우저가 handoff/deliverable 보존 기능을 제공하면 중단/최종 탭에 사용해 자동 정리로 재개 위치가 사라지지 않게 한다.

## 매일 승인 확인·Work 반영

1. 기존 목록에서 신청번호·수입자·동물/칩·여행을 대조해 현재 상세를 연다. UNDER REVIEW, 보완 요청, 반려, 승인, 발급을 구분한다. 보완 요청 본문·기한을 전부 읽는다.
2. 승인/발급된 실제 SPSIC를 내려받아 전 페이지·허가번호·수입자·칩·수량·운송/입국 조건·유효기간을 확인한다. 다운로드만 했거나 승인 이메일만 있다는 이유로 원본 검토 완료라고 하지 않는다.
3. Work의 정확한 여행 수입 항목과 보관함에 반영하고 DB로 재조회한다. 기존 UI/서버 저장 경로를 우선하며 DB 갱신이 필요하면 현재 액션의 저장 규약·권한을 확인하고 해당 필드만 보존 병합한다. 조회 스크립트를 쓰기 도구로 바꾸지 않는다.
4. 접수 시 신청일·진행, 실제 승인 및 원본 대조·보관 후 완료. **신청번호를 허가번호(`permit_no` 등)로 넣으면 잘못 완료될 수 있다.** 현재 `reportSlotStatusFor`와 저장 액션을 읽어 의미를 확인한다. 현재 UI는 `by_dest[여행 토큰]`과 레거시 값을 조합하므로 모든 국가 값을 덮어쓰지 않는다.
5. 기관 결과·Work 저장값이 다르면 차이·미반영 이유·다음 행동을 보고한다. 원본 보관 실패·허가 조건 불일치·접속 장애는 완료로 숨기지 않는다. 다른 담당의 일반 서류·내원 관리와 동일 케이스 잠금을 공유한다.
